
# ✅ 쿠폰 발급 시스템 부하 테스트 결과 보고서

## 1. 📌 테스트 개요

| 항목         | 내용 |
|--------------|------|
| **대상 기능** | 쿠폰 발급 API (동기 처리 구간) |
| **목적**     | 서버 스펙 산정, 병목 구간 분석, 스케일 아웃 기준 도출 |
| **도구**     | k6 + InfluxDB + Grafana + Docker |
| **조건**     | Peak 부하 시나리오: 1분간 10,000명 동시 트래픽 |

🧱 서버별 리소스 스펙

| 구성 요소 | ec2 인스턴스 타입 대상 | CPU    | Memory |
|-------|----------------|--------|--------|
| Redis | `c5.xlarge`    | 4 vCPU | 8GB   |
| Mysql | `c5.xlarge`    | 4 vCPU | 8GB   |
| Kafka | `c5.xlarge`    | 4 vCPU | 8GB   |
| Application POD   | `c5.xlarge`    | 4 vCPU | 4GB   |

✅ **테스트 목표**:
- 쿠폰 20,000건이 정상 발급되었는지 확인
- 목표 응답시간(P95 < 500ms)
- 목표 실패율 0%
- 위 지표에 충족하는 TPS 를 측정하여 스케일 아웃 기준 산정
---

## 2. 📊 테스트 조건별 결과

### [4,000 RPS]
- **kafka를 이용한 쿠폰 발급**

| 항목                            | 결과                        |
|-------------------------------|---------------------------|
| **TPS**                       | 약 850 TPS                 |
| **응답시간**                      | p(95) = **119.52ms** ✅    |
| **Dropped Iterations(요청 실패)** | 0 ✅                       |
| **Application POD CPU**       | CPU 320% 🚨 (*High Load*) |
| **Application POD 메모리**       | 1.5   GB 이하               |
| **kafka,mysql,redis CPU**     | CPU 100%  이하              |
| **kafka,mysql,redis 메모리**     | 1   GB 이하                 |
| **쿠폰 20,000건 정상 발급**          | ✅                         |

➡️ **성공 기준 충족. 4000 RPS 환경에서는 안정적으로 처리 가능**.  
➡️ **CPU에 비교적 높은 수치의 부하가 있으므로 CPU 스펙을 올리거나 오토스케일링 정책을 추가하여 안정적 운영 가능**.

- **kafka 도입 전 RDB/Redis 분산락을 이용한 쿠폰 발급**

| 항목                            | 결과                            |
|-------------------------------|-------------------------------|
| **TPS**                       | 약 300 TPS                     |
| **응답시간**                      | p(95) = **5.21초** ❌           |
| **Dropped Iterations(요청 실패)** | **29,961** 🚨  (전체 요청의 약 60%) |
| **Application POD CPU**       | CPU 420% ❌ (*High Load*)      |
| **Application POD 메모리**       | 1.5   GB 이하                   |
| **mysql,redis CPU**     | CPU 200%  이하                  |
| **mysql,redis 메모리**     | 1.9   GB 이하                   |
| **쿠폰 20,000건 정상 발급**          | ✅                             |
➡️ Application POD의 CPU 병목 발생
➡️ **성공 기준 불충족. kafka 를 이용한 쿠폰 발급 대비 TPS 가 약 3배정도 낮으며 서버 부하로 인해 전체 요청 중 60%가 서버에 도달하지 못함.
➡️ 1,000RPS 에서 약 300TPS의 성능을 보였으며 요청 실패 항목 없이 안정적 처리 가능.

---

### [5,000 RPS]
- **kafka를 이용한 쿠폰 발급**

| 항목                            | 결과                                                  |
|-------------------------------|-----------------------------------------------------|
| **TPS**                       | 약 650 TPS                                           |
| **응답시간**                      | p(95) = **3.54초** ❌                                 |
| **Dropped Iterations(요청 실패)** | **15,806** 🚨  (전체 요청의 약 20%)                       |
| **Application POD CPU**       | Application POD CPU 과부하 → *일시적 응답 정지 / 측정 불가* 현상 발생 |
| **Application POD 메모리**       | 안정적                                                 |
| **kafka,mysql,redis CPU**     | CPU 100%  이하                                        |
| **kafka,mysql,redis 메모리**     | 1   GB 이하                                           |
| **쿠폰 20,000건 정상 발급**          | ✅                                                   |

➡️ **Application POD의 CPU 병목 발생. 5,000 RPS 부터는 단일 인스턴스가 감당 불가**.

---

## 3. 🧠 주요 인사이트

- **kafka를 이용한 쿠폰 발급**
  - 4,000 RPS 에서 안정적인 성능을 보였으며 5,000 RPS 이상의 요청이 몰리면 Application POD 부하 발생.
  - ✅ Redis/Kafka/MySQL 서버 자원은 여유 있음 → Application POD가 병목의 핵심
  - ⚙️ Application POD 1대당 처리 가능한 TPS ≒ **850**
- **kafka 도입 전 RDB/Redis 분산락을 이용한 쿠폰 발급**
  - 1,000 RPS 에서 안정적인 성능을 보임.
  - ⚙️ Application POD 1대당 처리 가능한 TPS ≒ **300**
