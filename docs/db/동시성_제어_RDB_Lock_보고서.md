# 동시성 이슈 해결을 위한 RDB Lock 비교 보고서

### 1. 결제 시 주문 조회

## 문제 식별

- 특정 주문에 대한 결제가 완료되면, 해당 주문의 상태를 '완료'로 변경하는 로직을  
  하나의 트랜잭션 범위 내에서 처리하도록 설계했습니다.  
  결제 시에는 먼저 주문이 '완료' 상태인지 검증하고,  
  그렇지 않으면 예외를 반환하도록 처리하고 있습니다.  
  하지만 문제는 하나의 결제 트랜잭션이 아직 완료되기 전에 동일한 주문에 대한 결제 요청이 다시 들어오는 경우,    
  두 번째 요청도 '완료' 상태가 되기 전의 주문 상태를 읽게 되어,  
  결제가 중복으로 발생할 수 있는 위험이 존재합니다.

### 예시 상황
1.	사용자 A가 주문 1000('대기중' 상태)에 대한 결제 요청을 보냄 → 결제 트랜잭션 1 시작
2.	트랜잭션 커밋 전에 동일 주문 1000에 대해 결제 요청 -> 결제 트랜잭션 2 시작
3.	결제 트랜잭션 2도 '대기중' 상태를 조회
4.	결제 트랜잭션 1,결제 트랜잭션 2 모두 결제 로직을 진행하여 중복 결제 발생

### 해결방법
- 비관적 락(Pessimistic Lock) 적용하여 주문 레코드 조회 시 잠금 처리
```
💡하나의 결제 트랜잭션이 아직 완료되기 전에, 동일한 주문에 대한 결제 요청이 다시 들어오는 경우
비관적 락을 사용하면 주문 상태를 선점하여 제어할 수 있기 때문에,
결제 가능 여부에 따라 정확한 예외 처리가 가능합니다.

반면, 낙관적 락을 사용할 경우 두 트랜잭션 모두 동일하게 '결제 가능' 상태로 인식하고
비즈니스 로직을 정상적으로 수행한 뒤,
최종적으로 주문 상태를 커밋하는 시점에서 버전 충돌로 인해 예외가 발생하게 됩니다.
사용자는 결제 가능 여부에 대한 예외가 아닌 재시도 요청에 대한 예외를 받게 됩니다.
 
또한, 동일한 주문에 대한 중복 결제 요청은
실제 운영 상황에서 빈번하게 발생하는 동시성 이슈는 아니기 때문에,
비관적 락을 사용하더라도 시스템에 큰 부하가 발생하지 않습니다.

결제 시에는 쿠폰 사용, 포인트 차감, 재고 차감 등의 연계 로직이 함께 수행되는데,
낙관적락 사용시 오히려 비관적 락을 거는 것보다 높은 시스템 부하를 발생시킬 수 있습니다.

```

## 2. 포인트 충전

### 문제 식별
- 동일 사용자가 동시에 여러 충전 요청을 보내는 경우(발생 가능성 낮음)와  
  포인트 사용 요청과 트랜잭션 순서가 꼬이는 경우 데이터 정합성 이슈가 발생합니다.

### 예시 상황
1. 동일 사용자가 동시에 충전 요청을 보내는 경우
- 사용자 A가 포인트 조회(0원 반환) 후 1,000원 충전 요청을 보냄
- 같은 사용자 포인트 조회(0원 반환) 후  2,000원 충전 요청을 보냄 
- 최종적으로 3,000원이 아닌, 마지막 커밋된 값만 반영되어  
   1,000원 또는 2,000원만 적립되는 정합성 오류 발생

2. 포인트 사용 요청과 충전 요청의 트랜잭션 순서가 꼬이는 경우
- 사용자 B가 현재 포인트 포인트 조회 후(6,000 원 반환)상태에서 5,000원 사용 요청
- 사용 요청 트랜잭션이 끝나기 전 동일 사용자가 포인트 조회 후(6,000 원 반환)상태에서  
  2,000원 충전 요청
- 충전 트랜잭션  -> 사용 트랜잭션 순으로 트랜잭션 커밋
- 결과적으로 사용 요청이 반영되어 사용자 포인트는 1,000 저장

### 해결방법
- 비관적 락(Pessimistic Lock) 적용하여 포인트 레코드 조회 시 잠금 처리
```
💡포인트 충전 시 낙관적 락을 사용할 경우,
PG사를 통해 실제 결제가 완료된 이후 포인트 정보를 저장하는 단계에서
버전 충돌로 인해 트랜잭션이 실패할 수 있습니다.

이러한 상황이 발생하면,
이미 결제가 완료된 건에 대해 PG사를 통한 환불 처리를 별도로 진행해야 하며,
이 과정에서 추가적인 수수료 부담과 함께
결제 처리의 안정성에도 문제가 생길 수 있습니다.

따라서 결제와 포인트 저장의 정합성을 보장하기 위해
비관적 락을 적용한 설계 방식을 선택하였습니다.

또한 포인트 충전 시 발생할 수 있는 병목 요인은
PG사 응답 지연과 포인트 사용 시 적용된 비관적 락으로 인한 대기입니다.
하지만 이러한 병목은 낙관적 락을 적용한다고 해서 해결되는 문제가 아니기 때문에,
굳이 낙관적 락을 사용할 이유는 없습니다.

다만, 포인트 충전 시 비관적 락을 사용할 경우
PG사 응답 지연으로 인해 포인트 사용 로직에 불필요한 지연이 전파될 수 있습니다.
이를 방지하기 위해,
PG사 결제 응답을 받은 이후에 포인트 데이터에 비관적 락을 적용하도록 설계해야 합니다.

```

## 3. 결제 시 포인트 사용 , 쿠폰 사용, 상품 재고 차감

### 문제 식별
- 주문 결제 시 포인트 사용 , 쿠폰 사용, 상품 재고 차감를 하나의 트랜잭션에서 동작하도록  
설계 하였으며, 사용자가 다른 N개의 주문에 대한 결제를 각 트랜잭션이 끝나기 전에 모두 요청 했을 때  
포인트 정합성, 쿠폰 중복사용, 상품 재고 정합성 문제가 발생할 수 있습니다.

### 예시 상황
1.	사용자 A가 동시에 여러 주문(예: 주문 101, 102, 103)에 대해  
거의 동시에 결제 요청을 보냅니다.
2.	각 결제 요청은 포인트 사용, 쿠폰 사용, 상품 재고 차감을 포함한 하나의 트랜잭션으로 처리되며,
아직 첫 번째 주문(101)의 트랜잭션이 완료되기 전에 두 번째 주문(102)의 트랜잭션이 시작됩니다.
3.	이로 인해 다음과 같은 문제가 발생할 수 있습니다:  
   - 포인트 정합성 문제  
      - 주문 101에서 포인트 잔액(예: 10,000원) 포인트 5,000원을 사용하고 있음에도,  
        주문 102에서도 동일한 시점의 포인트 잔액(예: 10,000원)을 기준으로 사용을 시도  
      - 두 주문에서 모두 포인트가 사용되면 실제 잔액보다 초과 사용될 수 있음  
   - 쿠폰 중복 사용 문제  
      - 동일한 쿠폰을 주문 101과 102 양쪽에서 모두 사용 시도  
      - 두 트랜잭션이 동시에 쿠폰 사용 여부를 검증하면,  
        중복 사용 가능 
   - 상품 재고 정합성 문제  
      - 동일 상품에 대해 재고가 1개 남은 상태에서  
        두 주문이 거의 동시에 결제되며 각각 재고 차감 시도  
      - 재고가 음수가 되거나, 하나의 주문이 실패해야 하는데 둘 다 성공 처리됨

### 해결방법
- 비관적 락(Pessimistic Lock) 적용하여 포인트, 사용자 쿠폰, 상품 재고 레코드 조회 시 잠금 처리
```
💡낙관적락 사용을 사용하게 되면    
결제시 포인트 차감, 쿠폰사용, 상품 재고 차감 중 1개라도 버전 충돌 이슈가 발생하면    
전체 트랜잭션이 롤백 됩니다.
   
그 사이 다른 사용자가 해당 상품 재고를 모두 구입하면 공정성 이슈 발생할 수 있고  
서비스 핵심 로직인 결제에서, 결제가 가능한 상황임에도 불구하고  
시스템 인프라 기술로 인해 결제에 실패하면 사용자 경험에 안좋은 영향을 주게 됩니다.  
e-commerce 에서는 사용자 경험이 비즈니스에 중요한 부분이라고 판단하여 
낙관적 락에 비해 서버의 부하가 크더라도 비관적 락(Pessimistic Lock)을 사용하여 설계 하였습니다. 

```

## 4. 쿠폰 발급


### 문제 식별

- 발급 수량이 제한된 쿠폰의 경우,
  다수의 사용자가 동시에 발급을 시도하면 허용된 수량을 초과하여 발급될 수 있습니다.


### 예시 상황
1.	사용자 A, B가 동시에 쿠폰 발급 요청을 보냅니다.
2.	두 사용자 모두 쿠폰을 조회했을 때 **stock = 1**인 상태를 확인합니다.
3.	A, B 각각 다음과 같은 로직을 수행합니다:
```kotlin
if (coupon.stock > 0) {
    coupon.stock -= 1
    couponRepository.save(coupon)
}
```
4. 결과적으로, A와 B 모두 coupon.stock = 0 으로 설정한 후 저장합니다. (동시성 이슈 발생)
5. A,B 모두 쿠폰 발급에 성공합니다. 

### 해결방법

- 비관적 락(Pessimistic Lock) 적용하여 쿠폰 레코드 조회 시 잠금 처리
```

 💡쿠폰 발급은 대량의 트래픽이 집중되는 서비스로,
 동시다발적인 요청이 몰리는 상황이 빈번하게 발생할 수 있습니다.

 이러한 환경에서 낙관적 락(Optimistic Lock)을 사용하게 되면,
 트랜잭션 충돌로 인한 실패가 잦아지고,
 그에 따라 재시도 처리에 대한 부하를 시스템이 감당해야 합니다.
 또한 재시도 자체가 실패할 확률도 높기 때문에,
 결국 사용자 입장에서는 발급 실패 경험으로 만족도가 떨어지게 됩니다.
  
 비관적 락을 사용하게 되면 쿠폰 발급의 성공/실패 여부는 비즈니스 로직에 의해 제어가 됩니다.

 반면 낙관적 락을 사용한다면 인프라 계층의 기술이 쿠폰 발급의 성공/실패 여부에 영향을 주게 되는  
 단점이 있습니다.
 
 e-commerce 에서는 사용자 경험이 비즈니스에 중요한 부분이라고 판단하여 
 낙관적 락에 비해 서버의 부하가 크더라도 비관적 락(Pessimistic Lock)을 사용하여
 트랜잭션 충돌을 원천적으로 방지하고,
 정합성과 사용자 경험을 모두 확보하는 방향으로 설계하고자 합니다.
 
``` 

### 대안 
- 분산락 + DB 비관적 락 사용 
  - Redis를 이용해 다중 인스턴스 간 락 선점 제어 → 이후 DB 트랜잭션에서는 비관적 락을 통해 정합성 확보.
  - Redis 레벨에서 빠르게 경쟁 제어 가능 → DB 진입 트래픽 자체를 줄여 부하 완화
  - DB에서는 여전히 안전한 락 기반으로 초과 발급 방지
- PUB/SUB Message queue + DB 비관적 락 사용
  - 별도의 워커/컨슈머가 DB에 접근하여 발급 처리
  - 처리 순서 보장, DB 진입 트래픽 자체를 줄여 부하 완화
