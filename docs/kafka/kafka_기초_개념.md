# ✅ Kafka 기초 개념 & 동작 원리

## 📌 Kafka란?

* Kafka는 **대용량 실시간 데이터 스트림 처리**를 위한 **분산 스트리밍 플랫폼**.
* \*\*이벤트 중심 아키텍처(Event-Driven Architecture)\*\*의 핵심 구성 요소로 사용되며, 다양한 서비스들이 Kafka를 통해 데이터를 주고 받음.
* **Producer**가 발행한 이벤트를 **Broker**가 저장하고, **Consumer**가 필요한 시점에 데이터를 가져가는 구조.
* 이 구조 덕분에 **하나의 이벤트 발행으로 여러 서비스가 동시에 비동기적으로 반응**할 수 있어, 시스템 간 **강한 결합도를 낮추고 확장성 높은 서비스 구조**를 구현 할 수 있음.
* 핵심 특징:
    * 고가용성 (replication, 장애 시 자동 failover)
    * 높은 처리량 (batch 처리, zero-copy 전송)
    * 내구성 (디스크에 영속적으로 저장)
    * 유연한 소비 모델 (offset 기반, pull 방식)


## 📌 1-2. 구성 요소
| 구성요소               | 설명                                       |
| ------------------ |------------------------------------------|
| **Producer**       | 데이터를 Kafka에 전송하는 클라이언트                   |
| **Broker**         | Kafka 서버, 메시지를 저장하고 전송                   |
| **Topic**          | 메시지가 저장되는 논리적인 큐                         |
| **Partition**      | Topic 내부의 물리적인 단위 (병렬 처리 단위)             |
| **Consumer**       | 메시지를 읽는 클라이언트                            |
| **Consumer Group** | 하나의 메시지를 여러 인스턴스가 분산 처리할 수 있게 하는 단위      |
| **Zookeeper**      | (과거 버전) 클러스터 상태 관리 (v3.3.0 부터 KRaft로 전환) |

## 📌 1-3. 동작 원리 요약
```text
Producer → Topic(partition에 분산 저장됨) → ConsumerGroup이 병렬 소비
```

- Producer는 key에 따라 특정 파티션에 메시지를 전송
  - key에 따라 저장되는 파티션 보장 가능  

- Broker는 토픽의 파티션 단위로 메시지를 순서대로 저장

- Consumer는 토픽의 파티션 단위로 메시지를 오프셋 기반으로 소비


# ✅ Kafka 설정 정리 (기본값 기준)

## 📌 Broker (서버) 측 세팅

| 설정                          | 기본값          | 설명                               |
| --------------------------- | ------------ | -------------------------------- |
| `num.partitions`            | `1`          | 새 토픽 생성 시 기본 파티션 수               |
| `log.retention.ms`          | `604800000`  | 메시지 보관 시간 (7일)                   |
| `log.segment.bytes`         | `1073741824` | 로그 세그먼트 파일 최대 크기 (1GB)           |
| `log.retention.bytes`       | `-1`         | 최대 보관 용량 제한 (비활성화됨)              |
| `auto.create.topics.enable` | `true`       | 토픽이 없을 경우 자동 생성 여부               |
| `delete.topic.enable`       | `true`       | 토픽 삭제 가능 여부                      |
| `min.insync.replicas`       | `1`          | `acks=all` 일 때 최소 동기화된 replica 수 |

## 📌 Producer 세팅

| 설정                 | 기본값          | 설명                                                         |
| ------------------ | ------------ | ---------------------------------------------------------- |
| `acks`             | `1`          | 리더가 데이터를 받은 후 성공 응답 (`0`: no ack, `1`: leader만, `all`: 모두) |
| `retries`          | `2147483647` | 전송 실패 시 재시도 횟수                                             |
| `linger.ms`        | `0`          | 배치 전 최대 대기 시간 (ms)                                         |
| `batch.size`       | `16384`      | 배치 전송할 최대 메시지 크기 (bytes)                                   |
| `compression.type` | `none`       | 메시지 압축 방식 (`none`, `gzip`, `snappy`, `lz4`, `zstd`)        |

## 📌 Consumer 세팅

| 설정                   | 기본값               | 설명                                                      |
| -------------------- |-------------------|---------------------------------------------------------|
| `group.id`           | (필수 없음)           | 컨슈머가 속한 그룹 ID                                           |
| `auto.offset.reset`  | `latest`          | 초기 오프셋 없을 때 처리 방식 (`earliest`, `latest`, `none`)        |
| `enable.auto.commit` | `true`            | 자동 오프셋 커밋 여부                                            |
| `max.poll.records`   | `500`             | poll 당 가져올 최대 메시지 수                                     |
| `max.poll.interval.ms`   | `300000`             | poll() 호출 간 최대 허용 간격, 이 시간 동안 poll()이 호출되지 않으면 컨슈머가 실패한 것으로 간주되어 리밸런싱이 발생                                  |
| `session.timeout.ms` | `10000`           | 컨슈머 장애 탐지용 세션 타임아웃 (ms)                                 |
| `heartbeat.interval.ms`    | `3000`            | 컨슈머가 브로커에 보내는 heartbeat 간격. session.timeout.ms보다 짧아야 함. |
| `fetch.max.bytes`    | `52428800` (50MB) | 컨슈머가 브로커로부터 한 번에 가져올 수 있는 최대 바이트 수                      |


# ✅ 3. Kafka vs RabbitMQ vs Redis Pub/Sub
| 항목                     | Kafka                    | RabbitMQ                      | Redis Pub/Sub            |
|------------------------|--------------------------|-------------------------------|--------------------------|
| 메시지 저장              | 디스크 기반, durable          | 메모리 + 디스크 (옵션 설정 가능) | 메모리 only               |
| 처리량                  | 매우 높음                    | 낮음 (지연은 낮지만 처리량은 제한적) | 빠르지만 안정성은 낮음       |
| 확장성                  | 수평 확장 용이 (파티션 기반)        | 제한적 (sharding 어려움)         | 불가능                      |
| 지속성 (Durability)     | 오프셋 기반 로그 저장 가능          | 큐에 저장하여 일정 수준 유지 가능     | 지속 불가능                  |
| 재처리 (Replay)         | 가능 (오프셋으로 위치 제어, DLQ 구현) | 일부 가능 (Dead-letter Queue 활용) | 불가능                      |
| 컨슈머 그룹 지원         | 지원 (파티션 기반 병렬 처리 최적화)    | 지원                            | 미지원                      |
| 메시지 순서 보장         | 파티션 내 순서 보장              | 큐 내부 순서 보장                | 순서 보장 없음               |


## ✅ Kafka만의 핵심 장점 – Pull 기반 아키텍처
### 📌 Kafka: 컨슈머가 이벤트 소비를 제어
- Pull 기반 구조
  - → 컨슈머가 직접 poll() 요청을 통해 데이터를 가져감

- 오프셋 기반 처리
  - → "어디서부터", "언제", "얼마나" 읽을지를 컨슈머가 직접 제어 가능

- Throttling (속도 조절)
  - → 컨슈머 처리량에 맞춰 유연하게 소비, 서비스 안정성 확보

- 재처리 가능
  - → 같은 메시지를 오프셋 기준으로 반복 소비 가능 (Exactly-once or At-least-once 지원)

- 백프레셔 영향 없음
  - → 브로커는 단순 저장소 역할, 느린 컨슈머가 전체 성능에 영향 없음

### ❌ RabbitMQ / Redis PubSub: Push 기반 한계
####  📌 RabbitMQ – Push 기반 메시지 큐
- 브로커 → 컨슈머로 메시지 Push
  - 컨슈머가 처리할 준비가 안 돼도 메시지가 전송됨

- Backpressure 발생 가능
  - 컨슈머가 느리면 브로커에 메시지가 쌓이고 성능 저하

- 오프셋/재처리 제어 어려움
  - 메시지 재전송은 일부 큐에서만 제한적으로 가능함

####  📌 Redis Pub/Sub – 단방향 실시간 브로드캐스트
- 브로커가 실시간 Push
  - 구독자에게 실시간으로 메시지를 한 번만 전달

- 재시도/재처리 불가
  - 메시지를 못 받거나 처리 실패 시 복구 방법 없음

- 컨슈머 제어 불가
  - 메시지 소비 속도/순서를 제어할 수 없음
