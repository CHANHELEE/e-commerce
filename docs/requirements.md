# 📄 요구사항 정의서 - ecommerce 시스템

---

## ✅ 기능 요구사항
---

### 1️⃣ 잔액 충전 / 조회 API (`주요`)

- **기능**: 사용자의 충전 잔액을 관리하고 확인
- **조건**
  - 충전
    - 충전 금액은 1원 이상 10_000_000 이하의 값
    - 포인트 이력 적재와 포인트 충전 간 데이터 정합성 필요
  - 조회
    - 현재 포인트 및 포인트 이력을 조회



---

### 2️⃣ 상품 조회 API (`기본`)

- **기능**: 상품 목록 및 잔여 수량 확인
- **조건**
  - 조회 시점 기준의 최신 재고 수량 제공
  - 상품 기본정보 조회 가능 
  - 1가지 상품의 기본정보, 옵션, 재고 조회 가능

---

### 3️⃣ 선착순 쿠폰 기능 (`주요`)

- **기능**
  - **쿠폰 발급 API**: 선착순 조건으로 사용자에게 쿠폰 발급
  - **보유 쿠폰 조회 API**: 사용자가 가진 쿠폰 목록 반환
- **조건**
  - 발급 수량 제한 존재, 수량 만큼만 발급
  - 주문 시 쿠폰을 적용해 전체 금액 할인
  - 한명의 사용자가 동일한 쿠폰을 중복 발급 받을 수 없음
  - 쿠폰이 발급 되면 어떠한 수정도 불가 함

---

### 4️⃣ 주문 / 결제 API (`주요`)

- **기능**: 상품 주문 및 잔액 기반 결제 처리
- **조건**
  - **주문**
    - 주문시 재고,포인트,쿠폰에 대한 검증 
    - 쿠폰은 한번 사용 가능
    - 주문 상태에 따른 결제 상태 
      - 주문생성 : 결제 가능 
      - 주문실패 : 재결제 가능 
      - 주문성공 : 걸제 완료
    - 주문 실패 또는 주문 생성 상태가  
     일정 시간 유지 되면 주문은 삭제
  - **결제** 
    -  결제시 포인트, 쿠폰, 상품 재고 차감
   

  

---

### 5️⃣ 상위 상품 조회 API (`기본`)

- **기능**: 최근 3일간 가장 많이 팔린 상위 5개 상품 조회
- **조건**
  - 결제 완료된 주문 기준
  - 최근 3일 간의 정보: 매일 00시 기준 -3일
  - 상위 상품 조회 시 다른 기능의 부하를 최소화 해야 함


---

## ✅ 비기능 요구사항

| 항목         | 설명                                                                 |
|--------------|----------------------------------------------------------------------|
| 동시성 제어         | 동시 쿠폰 발급, 주문 처, 포인트 충전/차감 등에서 race condition 방지                ||
| 테스트       | 단위 및 통합 테스트 작성 |
| 확장성       | Redis, Kafka, 이벤트 시스템 연동을 고려한 구조 설계                   |
| 성능       | 일정 수준 이상의 트래픽에도 안정적으로 견딜 수 있는 성능을 확보해야 한다. (최적화된 DB 및 인프라 설계)|
