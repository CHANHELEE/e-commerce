## 📊 인기상품 캐싱 도입

### 📌 개요

기존 시스템에서는 인기상품 정보를 RDB 기반 테이블(popular_product)에 저장하고, 이를 직접 조회하는 구조로 설계 하였습니다. 하지만 트래픽 증가에 따라 다음과 같은 문제점이 발생할 수 있습니다.

- RDB 조회가 빈번해지면서 DB 부하 증가 (인기상품 데이터는 고빈도로 조회되지만 변경 주기는 낮음)

- 트래픽이 집중될 경우 RDB 성능 병목 우려

이를 해결하기 위해 Redis 기반 캐시 시스템을 도입하여 조회 성능을 개선하고, DB 부하를 효과적으로 분산하고자 하였습니다.

### ✅ 도입 전 문제점

| 항목        | 설명                                                               |
|-----------|------------------------------------------------------------------|
| **DB 부하** | 인기상품 조회 시마다 RDB 쿼리 발생  ( 트래픽이 몰릴 경우 DB connection pool 고갈 발생 가능) |
| **응답 속도** | 트래픽이 몰릴 경우 페이지 응답 지연 발생 가능성                                      |

### 🔧 개선 방안

- redis 캐시 도입
- 캐싱 전략
    - 인기상품 데이터를 캐싱
    - 캐시 조회 실패 시에만 RDB 접근 (Fallback)
    - 데이터 갱신 주기
        - 하루 1회, 변경 즉시 인기상품 테이블 및 Redis 캐시 갱신
- 캐시 저장 구조

| 항목        | 값                        |
|-----------|--------------------------|
| Redis Key | `cache:popular-products` |
| TTL       | 25시간 (갱신 실패 시 최소한 하루 보장) |

### 🔄 In-Memory Cache 대신 Redis를 선택한 이유

| 항목            | In-Memory Cache        | Redis                          |
|---------------|------------------------|--------------------------------|
| **인스턴스 간 공유** | ❌ 불가능 (각 인스턴스가 따로 가짐)  | ✅ 가능 (중앙 캐시)                   |
| **일관성 보장**    | ❌ 인스턴스 간 캐시 일관성 유지 어려움 | ✅ 캐시 갱신 즉시 모든 인스턴스에서 같은 데이터 조회 |
| **장애 복구**     | ❌ 인스턴스 재시작 시 캐시 손실     | ✅ Redis 자체에 데이터 유지 가능          |

-> **인기상품 데이터가 수정 되었을 경우 In-Memory Cache 사용 시 인스턴스간 데이터 불일치 문제 발생 가능**
